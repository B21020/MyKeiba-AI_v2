# 方針2：判断を遅らせられるかの確認と、票数の利用

計画：`C:\Users\koxyg\.claude\plans\giggly-baking-pancake.md`（承認済み）。前提は [オッズの動き](20261025_odds_movement.md)。実施日：2026年10月25日（実測は同日の開催）。

## 結論

1. **判断を6分前の配信より遅らせることはできない。**
   - 中間オッズの配信は11分前・6分前・1分前で固定されている。
   - 即PAT の締切は発走1分前で、1分前の配信は手元に届くのが締切の後（実測で発走後1分前後）。
   - 使える最後の配信は6分前のもの。
2. **6分前の配信が手元に届くのは、発走の4分20秒〜5分40秒前（17レース中12レースは4分20秒前後）。**
   - 事前に決めた基準「遅れの中央値 ≤ 60秒、最大 ≤ 120秒」は満たさない。中央値100秒、最大100秒。
   - ただし締切（発走1分前）までは3分20秒以上残る。判断を「発走4分前・6分前の配信」にすれば、全レースで間に合う。
   - これまでの検証は「発走5分前までに配信された最新＝6分前の配信」を使っているので、判断時刻を4分前に読み替えれば、結果はそのまま使える。判断時刻は「発走4分前・6分前の配信」と決めた（後述の決定）。
3. **6分前までの票数からは、直前の投票の兆候を読めない。**
   - 主の比較 [log q6, 11分前→6分前に入った額の割合] の ΔR² は −0.0003（95%区間 −0.0008〜+0.0001）。
   - 基準（区間の下限 > 0 かつ ≥ +0.002）に届かない。票数は使わずに方針1へ進む。
4. **6分前より後に入る投票には、市場全体を超える情報がある。しかし判断の時点では見えない。**
   - 単勝の最終の売上のうち、6分前の時点で入っているのは中央値41%。約6割が最後の6分間に入る。
   - その「6分前より後に入った額の割り振り」を足すと ΔR² +0.025（+0.019〜+0.032）。確定の市場の優位（+0.019）より大きい。
   - 確定の市場の優位は、直前に入る情報を持った投票によるもの。

## A. 判断時刻の確認

### 配信の時刻（開発期間の全2,562レース、0B41 の中間オッズ）

| 発走前の配信 | ある割合 |
|---|---|
| 16分前 | 20.6% |
| 11分前 | 99.9% |
| 6分前 | 99.7% |
| 1分前 | 97.2% |

10分前以降の配信の組み合わせ：(6, 1) が2,489レース、(6) だけが64、そのほか9。

### 発売の締切

即PAT・A-PAT は各レース発走1分前、JRAダイレクトは2分前（[JRA 発売時間](https://www.jra.go.jp/dento/soku/instructions/hatsubai/jra.html)）。

### 実測（2026年10月25日、東京・京都・新潟の17レース、10:10〜16:10発走）

方法（`tools/jvlink_live_latency.py`）:
- 各レースの発走15分前〜2分後に、20秒ごとに `JVRTOpen('0B41')` で読み、新しい配信を初めて受け取った時刻を記録した。
- 869回の読み取りはすべて成功し、1回の読み取りは中央値0.01秒だった。
- 利用キーは扱っていない。

| 配信 | レース数 | 発表時刻からの遅れ | 受け取ったときの発走までの残り |
|---|---|---|---|
| 11分前 | 17 | 80秒（全レース） | 9分40秒 |
| 6分前 | 17 | 20秒が5レース、80秒が1、100秒が11 | 5分40秒（5）、4分20秒〜4分40秒（12） |
| 1分前 | 17 | 100〜120秒 | 発走後40〜60秒（締切後） |

- 遅れは20秒刻みで測っている。発表時刻は分単位なので、実際の遅れは表より0〜60秒短い可能性がある。
- 6分前の配信は、遅くとも発走4分20秒前には届いた。締切まで3分20秒以上ある。

## B. 票数の利用

### データ

- O1 レコードの末尾に、単勝・複勝・枠連の票数合計（各11桁、単位百円、返還分を含む）がある（JV-Data 仕様書の O1、928・939・950バイト目）。
- 保存済みの原文3,642レースから、`tools/build_pool_table.py` で配信ごとの表を作った。JV-Link の追加取得はしていない。git 対象外。
- 検査:
  - 中間の配信で単勝の票数合計が減るレースが25ある（取消による返還と思われる）。
  - 締切後の値が最後の中間を下回るレースも25ある。
  - 解析エラーは0。

### 方法

- 各馬に売れた額を S_i(t) ≈ q_i(t)·W(t) と推定した（q＝1/オッズを正規化、W＝単勝票数合計）。
- 配信 a→b の間に入った額の割合 f_i から、`gap = log f − log q6` を作った。直前の投票が全体の割合より多く入った馬ほど正になる。
- 6分前に使えるもの：11→6分前（主）、20→11分前、30→20分前の gap。売上の規模・伸びと log q6 の交互作用。
- 説明だけ：6分前→締切後の gap（判断には使えない）。
- 区切り・評価は前回までと同じ（rolling の3つ、calib で条件付きロジットを推定 → outer、評価1,580レース）。

### 売上の入り方（開発期間2,110レース）

- 単勝の最終の売上は中央値約6,000万円。
- 最終の売上のうち、11分前までに入っているのは中央値26%、6分前までは41%（10〜90%点で30〜56%）。

人気別の gap（中央値）:

| 6分前の人気 | 勝率 | 11→6分前 | 6分前→締切後 |
|---|---|---|---|
| 1 | 30.5% | +0.04 | −0.03 |
| 2 | 20.0% | +0.05 | +0.08 |
| 3 | 12.6% | +0.03 | +0.02 |
| 4〜5 | 8.6% | −0.02 | −0.05 |
| 6〜8 | 4.6% | −0.13 | −0.23 |
| 9〜12 | 1.6% | −0.30 | −0.56 |
| 13〜18 | 0.6% | −0.48 | −0.93 |

直前の投票は人気馬（特に2番人気）に寄り、人気薄にはほとんど入らない。11→6分前と6分前→締切後の gap の相関は0.52。ただしその大半は、この人気による偏りで、log q6 がすでに持っている。

### 勝ち馬を当てる力（[log q6] に対する ΔR²）

| 足したもの | 1〜2月 | 3〜4月 | 5〜6月 | 合計（95%区間） |
|---|---|---|---|---|
| 11→6分前の gap（主） | +0.0001 | −0.0003 | −0.0008 | −0.0003（−0.0008〜+0.0001） |
| 3つの時間幅の gap | −0.0011 | −0.0011 | −0.0009 | −0.0010（−0.0019〜−0.0002） |
| 売上の規模・伸びとの交互作用 | −0.0011 | −0.0005 | −0.0010 | −0.0009（−0.0019〜+0.0001） |
| 全部 | −0.0023 | −0.0016 | −0.0017 | −0.0019（−0.0033〜−0.0006） |
| 6分前→締切後の gap（判断には使えない） | +0.0258 | +0.0250 | +0.0253 | +0.0254（+0.0188〜+0.0320） |
| 確定の市場（参考） | +0.0198 | +0.0187 | +0.0194 | +0.0193（+0.0157〜+0.0228） |

- 6分前より後の gap の係数は3期間とも約1.1で安定している。
- 11→6分前の gap の係数は +0.12／+0.14／−0.09 と符号が変わる。

購入（期待値 = 勝つ確率 × 6分前のオッズ）も、どの組でも回収率100%を上回る区間は無かった（`results.json`）。

## 決定：判断時刻（2026年10月25日、ユーザーが決定）

**判断は「発走4分前、6分前の配信」で行う。**
- 計画の基準（遅れの中央値 ≤ 60秒、最大 ≤ 120秒）は、文字どおりには満たさなかった（中央値100秒）。ただし、基準の目的は「6分前の配信を見てから投票できるか」。実測では全17レースで、締切（発走1分前）の3分20秒以上前に届いた。
- これまでの検証（段階2の再比較、複勝、オッズの動き、票数）は「発表が発走5分前以前の最新の配信＝6分前の配信」を使っているので、そのまま有効。コードの選び方（`tools/run_stage2_t6.py` の `DECISION_MIN = 5`）も変えない。
- 11分前の配信に下げる案は採らない。
- **確認**：受け取りの遅れはこの1日・17レースの値なので、次の開催日（10/31・11/1）にも `tools/jvlink_live_latency.py` で同じ計測を行う。6分前の配信が発走4分前までに届かないレースがあれば、判断時刻を見直す。
